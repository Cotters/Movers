# Watchlist organization

Sort films from the sort control beside the film count. Release date, alphabetical and rating support ascending/descending order. Recently added preserves the existing default. Missing/invalid dates and ratings stay last in either direction; title/id ties are deterministic. Sorting applies after local filtering in list and grid layouts.

Preferences are installation-local, independent of shared-list contents and activity. A feature-owned storage interface has Android/iOS adapters using the app's existing native-preferences pattern. Common policy serializes updates, persists before publishing new state and propagates cancellation. Feature ViewModels own selection/filtering; components render values and events. No database/backend migration or new library is needed.

Swipe a watchlist overview row to reveal Pin/Unpin on the right (the trailing edge, mirrored in RTL). Up to five personal pins appear first in pin order, with a pin marker and clear row/group separators. Further pins are disabled at the cap; unpinning remains available. The common preference policy enforces the limit under a mutex, and deleting/leaving a list releases its slot. The generic design-system reveal component is extracted from the existing film gesture; movie Add/Remove labels and delayed-write Undo policy stay unchanged. Accessibility actions provide the same pin controls. Home list rows reveal Add on the right and no longer have a permanent + button; grid cards retain +. Watchlist film rows retain their two-sided Add/Remove controls.

The later [full-swipe follow-up](swipe-actions.md#short-and-full-swipes) adds activation on deliberate long Add and Pin/Unpin swipes, with short reveal/tap retained. Remove remains tap-only; disabled pins never activate.

Watchlist search filters cached matches immediately, then shows an “Add to list” section with paged film-search results in the same scrolling container. New queries cancel old searches before a 600 ms debounce. Existing members and films awaiting removal Undo are excluded. Suggestions reuse the compact search row/poster and repository membership API; actions stay guarded until observed membership confirms the write. Query/results stay open for consecutive adds. Loading/errors/retry stay in the suggestions section, leaving local matches usable. A rendering guard prevents duplicate shared-image sources while paging catches up with a successful add.

Native preference writes and common-state publication finish as one small critical section before cancellation is rethrown. Retry/pruning uses successfully read list snapshots; a failed list read never clears saved pins. New test cases remain deferred; existing host/native verification and physical-device limits are recorded in the [handoff](../workflow/handoff.md).

References: [Compose gestures](https://developer.android.com/develop/ui/compose/touch-input/pointer-input/drag-composables), [native Android preferences](https://developer.android.com/training/data-storage/shared-preferences), [UserDefaults](https://developer.apple.com/documentation/foundation/userdefaults) and [coroutine Mutex](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.sync/-mutex/) and [Paging transformations](https://developer.android.com/topic/libraries/architecture/paging/v3-transform). Android's docs prefer DataStore for new general-purpose settings; this small feature follows the current project adapter pattern without a storage-library migration.
