# Working in Movers

- Start with [Human.md](docs/workflow/Human.md) for the agreed workflow. For substantial work or a resumed task, read [the handoff](docs/workflow/handoff.md) and verify its claims against the current source and Git state.
- Use [development guidance](docs/workflow/development.md) when making architecture or behavior changes, and [testing guidance](docs/workflow/testing.md) when choosing or running checks. Read only the references the task needs.
- When asked to work on the next thing, read the first unchecked item in private `Notes/Todo.md` if present, then inspect and agree its feature plan. Keep the queue succinct. If it is absent in a clone, use the tracked handoff; do not publish or force-add private notes.
- Clarify material product decisions and obtain agreement on a feature plan before implementation. Once agreed, complete the authorized work and host verification without repeatedly asking permission. Shared Watchlist implementation and Supabase provisioning require a separate feature request and agreed plan.
- Match the nearest relevant implementation: Compose screens, ViewModel state/events, focused use cases, repository contracts, Hilt, Room, and typed navigation. Preserve existing module boundaries; do not introduce a new architecture or upgrade dependencies incidentally.
- Consult current official Android documentation for Android API or tooling decisions. Use relevant installed skills selectively; user instructions take precedence. If Android CLI documentation access fails, use official web documentation and report material limits.
- **Never start, run, or interact with an emulator or simulator.** Do not run connected/instrumented tests yourself. Ask the user to verify Android runtime/UI behavior on their physical device, giving specific steps and required observations. Host tests, builds, static checks, and previews that do not start a device are allowed.
- Run `./scripts/verify.sh` for complete host verification; use focused Gradle checks during iteration. Fix setup/change-induced failures; record unrelated baseline issues rather than silently broadening scope or suppressing failures. Distinguish executed, cached, compiled-only, and pending checks.
- Keep credentials, local properties, and private `Notes/` content out of tracked files and reports. Never print real credential contents. CI uses a dummy TMDB constant and does not exercise the service.
- Treat this portfolio project as public source. Follow [backend portability guidance](docs/workflow/open-source.md): repositories depend on a vendor-neutral database API; Supabase-specific adapters sit behind that API and Hilt bindings. Publish reviewed setup/migration code and placeholders, never live data or privileged deployment credentials.
- Preserve cancellation propagation, user/session isolation, observable persisted state, and existing data when changing asynchronous or storage code. See the development guide for concrete examples.
- Before handoff, update durable decisions and verification evidence in `docs/workflow/handoff.md`. Update the relevant guide when an agreed workflow changes. Preserve Human.md feedback; review it for workflow changes, and label proposals separately from accepted rules. Do not treat a proposal as authorization for unrelated changes.
- Keep changes focused and comments sparse: explain non-obvious constraints or rationale, not obvious control flow. Keep the user's unrelated edits intact.
